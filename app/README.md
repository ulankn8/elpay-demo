# ЭлPay — мобильное приложение (Flutter)

Нативное приложение под **Android и iOS** из одного кода. Собрано по утверждённому
прототипу (`../index.html`): коммуналка, садик и школа, налоги, билеты. Пилот — Ош.

**Платежи и вход — заглушки.** Платёжный шлюз и боевой OTP не подключены:
`StubPaymentsRepository` и `MockAuthRepository` имитируют ответ, а интерфейс честно
об этом предупреждает. Всё остальное работает по-настоящему: слой данных, кэш,
офлайн-режим и подключение счетов.

## Что уже есть

- **Вход:** телефон, почта и Telegram, код из четырёх цифр (в демо — `4815`), знакомство
  (имя, город, адрес).
- **Подключение счетов:** поиск по лицевому счёту и по адресу, подтверждение
  владения кодом, подключение к объекту, список подключённых со статусом
  синхронизации, отключение, обновление начислений.
- **Главная:** сторисы (в одной рамке до трёх кадров), карточки объектов с разбивкой
  по услугам, «Новая оплата» и круглые значки услуг, обновление потягиванием.
- **Оплата по шагам:** карточка объекта → список услуг с галочками → разбор услуги
  (за что платим, как начислено, реквизиты) → способ оплаты → готово.
  Способ подставляется из профиля и меняется на последнем шаге.
- **Платежи:** кошелёк с пополнением, история, автоплатежи, способы оплаты, маркет.
- **История и отчёты:** поиск и фильтры, квитанция по каждому платежу, отчёт за месяц и год
  с разбивкой по категориям и объектам.
- **Маркет:** афиша Оша, покупка билета, QR-билет на входе, возврат.
- **Профиль:** личные данные, объекты, счета и реквизиты, адреса, семейный доступ,
  безопасность (код-пароль, Face ID, подтверждение крупных платежей), устройства,
  уведомления, тарифы, поддержка, удаление аккаунта.
- **Два языка** (русский и кыргызский) и **тёмная тема**.
- **Работа без сети:** данные показываются из кэша с честной плашкой, действия
  копятся в очереди и уходят, когда связь появится (демо-переключатель — в профиле).

В том же пакете живёт **кабинет служб** — веб-приложение для водоканала и других
служб: `lib/admin/`, точка входа `lib/admin/main_admin.dart`, описание — [`ADMIN.md`](ADMIN.md).

## Запуск

```bash
flutter pub get
flutter run                 # на подключённом телефоне или эмуляторе
flutter run -d chrome       # быстрый просмотр в браузере
```

Сборки:

```bash
flutter build apk --release        # Android
flutter build appbundle --release  # Google Play
flutter build ipa                  # iOS, нужен macOS и Xcode
flutter build web                  # веб-демо
```

## Проверка

```bash
flutter analyze   # статический анализ, должно быть «No issues found»
flutter test      # ядро, кэш, очередь, правила подключения счетов, экраны
```

Анализ идёт в строгом режиме типов (`strict-casts` и `strict-raw-types` в
`analysis_options.yaml`): разбор JSON написан руками, и без этих флагов
`as Map` вместо `as Map<String, dynamic>` ловится только падением на устройстве.

## Как устроено

Подробности — в [ARCHITECTURE.md](ARCHITECTURE.md): слои, ошибки, кэш, офлайн
и что менять, когда появятся боевой бэкенд и платёжный шлюз.

| Папка | Что внутри |
|---|---|
| `lib/core` | Токены бренда, тема, форматы сумм и дат, хранилище настроек, общие виджеты, переводы. |
| `lib/data` | Модели, демо-данные и реестр счетов, контракт бэкенда `api/elpay_api.dart` с мок- и HTTP-реализациями, репозитории с кэшем. |
| `lib/state` | Состояние на Riverpod: сессия, счета, кошелёк, история, семья, безопасность. |
| `lib/features` | Экраны по разделам: `auth`, `home`, `bills`, `payments`, `history`, `reports`, `market`, `notices`, `profile`, `shell`. |

Данные идут через контракт `ElPayApi`: в демо отвечает `MockElPayApi`, в бою —
`HttpElPayApi`. Переключение флагом сборки, без правок кода:

```bash
flutter build apk --dart-define=API_BASE_URL=https://api.elpay.kg/v1 \
                  --dart-define=USE_MOCK=false
```

Репозитории возвращают `Result<T>` — ошибку нельзя забыть обработать;
`LocalStore` держит кэш, `Outbox` — очередь офлайн-действий. `LocalStore` —
контракт, а не класс: в бою это `PrefsLocalStore` поверх `SharedPreferences`,
в тестах `MemoryLocalStore` (поэтому тесты кэша и очереди не поднимают
биндинг Flutter), а когда данных станет много, рядом встанет SQLite.
Подробности подмены источника — в разделе «Как подменить демо на бой».

Переводы — типизированный класс `S` (`lib/core/l10n/s.dart`): новая строка не
скомпилируется, пока её не добавят в оба языка. Демо-данные переводятся словарём `s.tr()`.

## Эндпоинты бэкенда

Контракт источника данных — `lib/data/api/elpay_api.dart`: одна поверхность
у демо-реализации (`MockElPayApi`) и у боевой (`HttpElPayApi`). Адреса
зафиксированы в `http_api.dart` — это и есть спецификация для бэкенд-команды.
База берётся из `API_BASE_URL`, по умолчанию `https://api.elpay.kg/v1`.

| Метод | Путь | Параметры и тело | Ответ |
|---|---|---|---|
| GET | `/objects` | — | массив `PayObject` — объекты пользователя (Дом, Родители) |
| GET | `/bills` | — | массив `Bill` — начисления по подключённым счетам |
| GET | `/accounts` | — | массив `ConnectedAccount` — подключённые лицевые счета |
| GET | `/accounts/search` | по номеру: `account`, `provider`; по адресу: `city`, `street`, `house`, `flat`, `provider` | массив `AccountCandidate` |
| POST | `/accounts/confirm` | `{candidateId, code}` | `AccountCandidate` уже без требования кода |
| POST | `/accounts/connect` | `{candidateId, objectId}` | `{account, bill?}` |
| DELETE | `/accounts/{id}` | — | пустое тело или `{}` |
| POST | `/accounts/sync` | — | `{bills, accounts, syncedAt}` |
| GET | `/payments` | — | массив `Payment` — история |
| GET | `/catalog` | `locale` | категории, поставщики, быстрые услуги, способы оплаты, реквизиты банка, маски лицевых счетов |

`/catalog` появляется вместе с `CatalogRepository` — он снимает последний
прямой импорт демо-данных из экранов оплаты. Остальные девять адресов уже
реализованы в `http_api.dart` и ждут только живого сервера.

Требования, без которых клиент будет работать неправильно:

- **Коды ответов.** 401 и 403 → повторный вход; 404 → «не найдено»; 5xx →
  «сервер не ответил», клиент сам делает два повтора с нарастающей паузой;
  4xx с телом `{"field": "...", "message": "..."}` → ошибка валидации садится
  под конкретное поле формы. На 4xx повторов нет — неверный номер счёта от
  повтора верным не станет. Таймаут запроса — 20 с (`TIMEOUT_S`).
- **`Idempotency-Key` на каждом POST, меняющем состояние** (подключение счёта,
  оплата). Ключ случайный, один на попытку пользователя (`lib/core/ids.dart`),
  и повтор по кнопке, и повтор из офлайн-очереди идут с тем же ключом. Сервер
  обязан вернуть результат первой операции, а не провести её второй раз.
- **`bill` в ответе `/accounts/connect` — только при реальном начислении.** Счёт
  без выставленного начисления подключать можно, но `Bill` на 0 сом создавать
  нельзя: такой счёт попадает в список «к оплате» и ломает разбивку на главной.
- **`Bill.accountId`** обязателен: начисление ссылается на счёт по id, а не на
  строку номера. Иначе после переподключения начисления не находятся.
- **Суммы — числа, а не строки.** Деньги в клиенте пока `double` (см. долги ниже).
- **Ответ всегда JSON.** Пустое тело допустимо только у `DELETE`.
- **Даты — ISO 8601.** Неразобранная дата не роняет экран, но и не отображается
  правильно, поэтому расхождений в формате быть не должно.

## Как подменить демо на бой

Шов один — провайдер источника в `lib/state/providers.dart`:

```dart
// демо: отвечает реестр из data/registry_data.dart, сеть не нужна
final apiProvider = Provider<ElPayApi>((ref) => MockElPayApi(...));
// бой: те же методы поверх HTTP
final apiProvider = Provider<ElPayApi>((ref) => HttpElPayApi(ApiClient()));
```

Выбор делает флаг сборки, править код не нужно:

```bash
flutter build apk --release \
  --dart-define=API_BASE_URL=https://api.elpay.kg/v1 \
  --dart-define=USE_MOCK=false \
  --dart-define=PAYMENTS_ENABLED=true \
  --dart-define=REAL_AUTH_ENABLED=true \
  --dart-define=VERBOSE_LOGS=false
```

Ниже провайдера не меняется ничего. Политика доставки данных — кэш, потом
сеть; офлайн-очередь; идемпотентность; маппинг ошибок — написана один раз
в репозиториях, и в демо исполняется ТА ЖЕ, что в бою. Поэтому офлайн-путь,
который калится на каждом показе, — ровно тот путь, который встретит живой
бэкенд. Если демо-режим когда-нибудь получит свои репозитории вместо своего
источника, это свойство исчезнет, и месяц эксплуатации проверит только мок.

Что остаётся заглушкой и чем подменяется:

| Заглушка | Чем подменить | Как подготовлено |
|---|---|---|
| `StubPaymentsRepository` | боевой платёжный шлюз | форма контракта подгоняется под бой (`Result`, признак `isStub`, идентификатор операции, частичная сумма, запрос статуса), чтобы подстановка была одной строкой в `paymentsRepoProvider`, а экраны не правились |
| `MockAuthRepository`, код `4815` | боевой OTP и вход через Telegram | тот же `Result`-контракт, сессия хранится в `AppPrefs`; токены ждут `flutter_secure_storage` |

Проверить обе заглушки здесь нельзя по-настоящему: Android SDK в контейнере
нет, iOS требует macOS. Это ровно те две вещи, которые нужно прокликать
на живом устройстве перед показом.

## Записанные долги

Названы, а не спрятаны: каждый — решение, а не забытое место.

- **Деньги — `double`.** Для процессинга правильнее целые тыйыны, но переход
  тянет `core/format.dart`, виджет `Amount`, все фикстуры и `test/format_test.dart`
  (он фиксирует формат `4 449,44` с обычными пробелами). Делаем перед
  подключением шлюза: сейчас это чистый рефакторинг, а после шлюза — уже
  правка денежной логики, то есть риск на живых платежах.
- **Токенов в `Session` нет** — потому что нет боевого входа. Вместе с ними
  понадобится `flutter_secure_storage`: единственный обязательный будущий
  пакет, `SharedPreferences` для токенов не годится.
- **Репозиториев истории, уведомлений, билетов, семьи, устройств и адресов нет.**
  Эти экраны берут данные из состояния напрямую. Смена типа провайдера затронет
  историю, отчёты, уведомления и маркет, а продуктовой пользы сейчас ноль —
  заводим, когда у бэкенда появятся соответствующие эндпоинты.
- **Период начисления — строка** (`'Сентябрь 2026'`), а не пара дат. Сортировать
  и сравнивать периоды нельзя, отчёт за квартал на этом не построить.
- **Кодогенерации нет совсем:** ни `freezed`, ни `json_serializable`, ни
  `build_runner`, ни `riverpod_generator`. `fromJson`/`toJson` написаны руками,
  поэтому за ними следит строгий режим типов, а не генератор.
